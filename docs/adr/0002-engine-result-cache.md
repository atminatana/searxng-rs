# ADR 0002: кэш результатов движков

- **Дата:** 2026-10-07
- **Статус:** Accepted (решение владельца: ТЗ `2026-10-07-engine-trust`, Р2(а))
- **Тема:** `src/search/cache.rs`, отступление от эталона SearXNG (в нём кэша
  результатов нет)

## Контекст

Основные клиенты инструмента — LLM-агенты через MCP. Они часто повторяют один
и тот же запрос (переформулировка плана, повтор после ошибки инструмента,
несколько агентов с одной задачей). Каждый повтор уходил в поисковик и считался
там ещё одним запросом с того же IP; поисковики отвечают на такие серии
капчей и HTTP 403/429 (см. ADR 0001 и живые проверки 2026-10-07).

## Решение

Успешные результаты каждого движка кэшируются на `search.cache_ttl` секунд
(по умолчанию 300) по ключу «движок + текст запроса + язык + safesearch +
страница + категория». Размер ограничен `search.cache_max_entries`
(по умолчанию 1000); при переполнении вытесняются самые старые записи.
Ошибки не кэшируются. Значение 0 отключает кэш.

## Альтернативы и обоснование

1. **Без кэша (как в SearXNG)** — отвергнуто: SearXNG рассчитан на людей
   в браузере, у которых повторы редки; у LLM-клиентов они обычны.
2. **Кэш целого ответа поиска** — отвергнуто: ответ зависит от набора
   движков; кэш по движку переиспользуется между запросами с разными
   наборами и не теряется, когда один из движков приостановлен.
3. **Кэш по движку (выбрано)** — минимальная единица, которая сокращает
   число внешних запросов без изменения формата ответа.

## Последствия

- **Плюсы:** повтор запроса не создаёт внешнего трафика и отвечает мгновенно
  (живая проверка: 0.56 с → 0.002 с).
- **Минусы/риски:** в пределах TTL клиент может получить выдачу
  пятиминутной давности; память — до `cache_max_entries` ответов на процесс.
  Кэш живёт в процессе и не разделяется между экземплярами сервера.
